# 技术调研：新项目立即获得可玩模板

## 决策 1：复用现有固定模板准备器

**决定**：复用 `FixedProjectProvisioner.prepare()` 和 `build()`，不写第二套模板复制或 npm 安装逻辑；只补充一个受控阶段回调，以便界面区分模板复制和依赖准备。

**理由**：现有实现已经限制模板来源、固定依赖清单、npm 参数、生命周期脚本、路径和符号链接，并具有超时、停止、依赖标记和幂等检查。新功能缺的是“新建后自动编排和展示状态”，不是底层模板能力。

**考虑过的替代方案**：复制一份已经带 `node_modules` 或 `dist` 的完整项目。拒绝原因是体积、跨平台原生依赖、完整性和版本一致性风险更高。

## 决策 2：创建记录先返回，准备在 Main 中继续

**决定**：项目记录安全落盘后立即返回，Main 自动排队准备并通过 `project:updated` 推送进度。

**理由**：首次依赖安装最长可达数分钟。让 `project:create` 一直等待会让新建弹窗像卡死，也不利于失败后保留项目。先持久化还能满足应用退出后识别中断状态。

**考虑过的替代方案**：让 Renderer 连续调用“创建、准备、构建、验证”。拒绝原因是 Renderer 会承担业务编排，刷新、关闭弹窗或切换项目容易让状态丢失，也扩大 IPC 权限面。

## 决策 3：准备状态独立于 Agent 状态

**决定**：在 `ProjectRecord` 增加可选 `starterPreparation`，不复用 `ProjectStatus` 和 `PipelineStageId`。

**理由**：现有 `status/stage` 描述 Agent 会话。模板准备不使用 Agent，也可能在 Agent 从未启动时运行。混用会让界面和恢复逻辑误以为 Agent 正在运行，并破坏已有单槽调度语义。

**考虑过的替代方案**：扩展现有 stage 加“依赖安装”。拒绝原因是 Agent Pipeline 和新建准备的生命周期不同，停止、重试和历史兼容也不同。

## 决策 4：历史项目用“字段缺失”表示未受本功能管理

**决定**：`starterPreparation` 对持久化旧数据为可选；缺失时保持历史项目现有行为，不自动准备或门禁。

**理由**：无法只凭旧的文字状态可靠判断磁盘上是否有完整游戏。自动复制或构建可能覆盖用户改过的依赖文件。显式兼容默认既保护现有项目，也为后续“用户主动检查并修复历史项目”保留空间。

**考虑过的替代方案**：启动时扫描所有历史项目并自动标记 ready 或修复。拒绝原因是扫描和构建有副作用、成本高，且违反不知情时不覆盖历史项目的需求。

## 决策 5：严格真实关卡读取，不改变通用读取语义

**决定**：准备服务增加仅供成功验证使用的“关卡文件必须存在”检查；不在本功能中全局删除 `LevelDocumentStore.read()` 的默认关卡回退。Renderer 对未 ready 的新项目不调用读取。

**理由**：现有默认回退可能被其他旧流程依赖。通过状态门禁和准备服务的严格检查，可以让新项目的虚假默认展示为 0，同时避免扩大兼容性影响。

**考虑过的替代方案**：让所有缺少 `src/level.json` 的读取都报错。拒绝原因是会改变历史项目和既有测试契约，超出本功能范围。

## 决策 6：进程内去重并串行准备

**决定**：同项目请求合并；不同项目按一个进程内队列串行执行。队列不跨重启恢复，重启后只转换为可重试状态。

**理由**：避免重复复制和多个 npm 构建互相争用资源。崩溃后自动恢复命令会绕过用户的再次确认，因此只恢复数据状态，不自动恢复副作用。

**考虑过的替代方案**：允许每个项目并行安装。拒绝原因是当前桌面产品规模不需要该复杂度，且会使进度、退出和资源压力更难控制。

## 决策 7：成功由磁盘和实际 HTTP 探测共同证明

**决定**：依次完成模板/依赖、构建、严格关卡读取、真实本地试玩探测后才设置 ready。

**理由**：只有文件复制成功不能证明能构建；只有 `dist/` 存在不能证明入口有效；只有状态字段更不能证明用户能玩。多层证据直接对应“不可假成功”的产品要求。

**考虑过的替代方案**：构建命令退出码为 0 即成功。拒绝原因是残留或不完整产物仍可能无法由浏览器加载。
