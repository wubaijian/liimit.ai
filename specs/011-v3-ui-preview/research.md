# Research: 多游戏类型界面预览

## 决策 1：规划中的 Godot 项目不进入真实项目数据

**Decision**: Godot 迷宫使用独立的界面预览对象，只保留项目名称、创建方式和页面选择等临时状态；它不使用 `ProjectRecord`，也不加入项目列表。

**Rationale**: `ProjectRecord` 当前代表已经可以在本机创建、编辑和试玩的 Phaser 项目。把预览伪装成真实记录会违反产品事实，并可能触发准备、文件读取和 Agent 副作用。

**Alternatives considered**: 为 `ProductModeId` 增加 Godot 类型（会形成未实现的持久化契约）；创建假的项目记录（容易被误认为已交付）。

## 决策 2：保留 Phaser 创建链路，按类型分流提交

**Decision**: 新建窗口可以选择两种类型。横版类型继续调用现有 `onCreate`；迷宫类型只调用新的本地 `onPreviewGodot` 回调并关闭窗口。

**Rationale**: 用户可以真实验证现有产品，同时预览下一版界面，二者边界清楚且不需要修改主进程。

**Alternatives considered**: 把两种类型都做成纯预览（会破坏现有可用功能）；为 Godot 增加临时后台处理（超出本轮授权）。

## 决策 3：有限交互用于解释结构，不模拟真实执行

**Decision**: 允许切换关卡、选中物体、打开 AI/试玩/验证/导出面板和查看提示；保存、生成、构建、验证、AI 修改和导出始终只返回“不会真实执行”的反馈。

**Rationale**: 静态图片不足以验证信息架构，而假装成功会让用户错误理解完成程度。

**Alternatives considered**: 全部按钮禁用（难以体验流程）；用计时器伪造真实任务（会制造错误能力声明）。

## 决策 4：预览使用本地 HTML/CSS 图形

**Decision**: 示例迷宫、墙体、钥匙、门、敌人和出口由本地界面元素绘制，不加载远程网页、Godot 运行时或新素材。

**Rationale**: 这能保持离线、快速和安全，并符合“只增加 UI”的范围。

**Alternatives considered**: 嵌入 Godot Web 示例（属于真实运行时接入）；使用外部原型链接（引入网络和信任边界）。

## 决策 5：产品事实提示必须始终可见

**Decision**: 迷宫类型卡、预览顶部、流程弹层和动作反馈都使用一致的“界面预览 · 尚未接入”口径；真实 Phaser 卡使用“当前可用”。

**Rationale**: 用户在任何入口或截图中都应能判断当前能力状态。

**Alternatives considered**: 只在首次弹窗提示一次（后续截图和单独页面会丢失上下文）。
