# Research: 自定义音效描述

## 决策一：描述由用户填写，但添加固定安全约束

- **Decision**: 将去除首尾空格后的用户描述作为主要生成要求，并附加“短游戏音效、无语音、无环境铺底、尽量少留白”的固定约束。
- **Rationale**: 用户能控制风格和感觉，同时产品继续只生成 V3.1 范围内的短音效，不扩展到配音或背景音乐。
- **Alternatives considered**: 完全原样发送用户描述会扩大范围；继续使用六条固定提示词则不能满足本步骤目标。

## 决策二：描述只临时存在，不记录原文

- **Decision**: 描述只存在于设置窗口的组件状态和一次 IPC/网络请求中，不写用量记录、项目文件或错误信息。
- **Rationale**: 满足凭据与提示词不进入本机遥测的项目规则，也让本步骤不引入数据迁移。
- **Alternatives considered**: 保存最近描述便于重用，但这属于生成记录的后续步骤，会扩大当前范围。

## 决策三：使用双层校验

- **Decision**: Renderer 提供即时空值/字数提示；Main 使用独立校验再次约束 1～300 个字符并拒绝 C0/C1 控制字符。
- **Rationale**: 界面校验改善体验，Main 校验守住 Electron 信任边界。
- **Alternatives considered**: 只在 Renderer 校验无法阻止被篡改的调用；只在 Main 校验会让用户到点击后才知道问题。

## 决策四：本步骤保持一条、0.5 秒

- **Decision**: 不同时加入三候选和时长选择。
- **Rationale**: 用户明确要求逐步完成；保持小步可以单独验证描述链路，不消耗额外 API 次数。
- **Alternatives considered**: 一次完成整份 PRD 会把候选状态、取消、费用和交互同时混入，增加回归风险。
